# m3 · v0.3 — AI-native scheduling

**Goal:** make connex the effortless launcher for small AI clusters — the thing
that answers "which machines, what memory, what accelerator, how do I start a
worker on each" so MLX, llama.cpp, and torchrun don't have to. Detail in
[docs/05-ai-workloads.md](../../docs/05-ai-workloads.md).

## Items

- [`CX-SYS-030`] — `info` grows `mem_free_gb`, `gpu`, `accel`. Real allocatable
  memory (not just total), chip/VRAM name, and `metal|cuda|none` so launchers pick
  backends. This is the data every AI decision below depends on.
- [`CX-SCHED-030`] — `run --mem N` and `--arch` placement filters, applied before
  scoring. `--mem 48` is what makes "put this model where it fits" a one-liner.
- [`CX-CLIENT-030`] — link-speed awareness: prefer the wired/bridge address when a
  peer resolves on several, show an approximate link type in `ls`, and tie-break
  scoring toward the faster link. Keeps users from being surprised by Wi-Fi.
- [`CX-AI-030`] — `connex hostfile` and `connex mpirun` sugar: turn `ls --json`
  into an MLX/torchrun host list and launch ranked hosts with streamed logs, so
  distributed inference is two commands instead of a page of setup.

## Definition of done

- `connex ls --json` reports free memory and accelerator for every machine.
- `connex run --mem 48 -- ...` refuses machines that can't hold the job and places
  it on one that can.
- `connex mpirun -- python -m mlx_lm.generate ...` runs across the cluster with no
  hand-written hostfile.

## The honest note this milestone keeps repeating

Tensor-parallel across machines is bandwidth-hungry and disappointing over Wi-Fi;
pipeline/layer splits over a Thunderbolt cable are the sweet spot. connex surfaces
link type so the tooling and the user choose with eyes open, and prefers the cable
automatically.
